# The Last Light rule runtime

LIVEFORGE generates a versioned `RuleProgram` from a viewer's supported idea. Source is JSON or a TypeScript-shaped object literal (`export default { ... } satisfies RuleModule`). The compiler parses literals into a strict, bounded schema. It never runs generated JavaScript. Functions, expressions, imports, loops, prototype properties, spreads and getters are outside the grammar. An infinite loop is rejected as syntax rather than executed and interrupted.

The original plan suggested QuickJS and Phaser. This implementation uses a capability-limited intermediate representation and original Canvas2D artwork. A dedicated Web Worker owns a fixed 60 Hz simulation; React and the renderer consume snapshots rather than owning frame-by-frame physics. Canvas2D keeps the authored suspended-foundry scene portable without additional art or rendering dependencies. This is a bounded composition engine, not arbitrary game-code generation.

The six generic actions project an entity's shadow through an enabled lantern onto its supporting plane, create a relative temporary surface, add bounded impulse, change friction/bounce, apply a visual cue, or set an entity countdown. Compound conditions inspect entity scalars and compose `all`, `any`, `not`, and comparisons. The engine has no `shadowBridge` action. The practice sample supplies the relationship between prop stillness, physical shadow projection and collision. Baseline cosmetic shadows never create collision.

Limits: 24,000 source characters, depth 16, 1,600 tree nodes, eight clauses, six actions per clause, six children per compound condition, 16 queried entities, 128 commands per tick, 48 active generated surfaces, surface lifetime 120 ticks, projected length 480 world units, impulse components ±2 and velocity ±12. Numbers must be finite. Action batches are applied to a copy and committed only after bounds validation. Generated actions cannot delete the courier, edit the ember, teleport, edit progress, write checkpoints, call the network, or reach files, process state, the DOM or provider secrets. This structural boundary is narrower than a general JavaScript sandbox.

`verifyRuleProgram` is a trusted engine harness. It validates the schema independently of candidate claims, simulates four input scenarios against baseline worlds and requires an actual observable difference, compares deterministic replays, restores an exact pre-activation checkpoint, round-trips serialization and checks temporary collision cleanup. The report includes actual simulated tick and applied-effect counts. These checks establish bounded behavior and recovery on the supported fixture; they do not prove global level solvability or that a candidate implements every nuance of natural-language intent.

The game remains playable without a generated program: the lower stepping-stone route crosses both gaps. Generated surfaces can offer shortcuts. A/D or arrows move, Space jumps, E moves a nearby counterweight or toggles the lantern, and R recovers the ember at the most recent checkpoint. There are three checkpoint regions. In Counterweight Hall, E turns an authored crank and raises a causeway; at the final island, offering the ember with E wakes the Warden and opens the final passage to the Astral Hearth. Encounter state is serialized with the world and is outside the generated action capabilities. Recovery retains progress and the ember.

The client accepts an exact program and artifact hash for preview. The server must bind creator approval to that exact immutable artifact identity. The live game handle exposes `activate(program, artifactHash)`, `checkpoint()`, `restore(checkpoint)`, `pause(value)`, `reset()` and `rollback()`. `activate` snapshots the prior world and validates a copied candidate state before committing. `rollback` restores that exact world/program pair. The worker reports checkpoints, snapshots and faults; a runtime fault retires the law, restores its prior checkpoint and pauses the authority. Artifact hashing and authorization are backend responsibilities. Browser identity is not a substitute for server approval.

Practice source is deliberately prewritten and exported as `PRACTICE_RULE_SOURCE`. It must be labeled as a practice sample in product surfaces and must never be described as generated provider output. Candidate previews use their exact compiled program, including conditions and numeric parameters.

All scene art is original procedural Canvas2D work in `src/game/renderer.ts`; no external image, font, audio or game-asset license is required for those visuals.
