# The Last Light rule runtime — engine 2

LIVEFORGE generates a `RuleProgram` as JSON or a TypeScript-shaped literal (`export default { ... } satisfies RuleModule`). The compiler parses data into a strict bounded schema. Generated JavaScript is never executed: functions, imports, getters, loops, spreads and executable expressions are outside the grammar. Arithmetic is represented by validated data nodes. Infinite loops are rejected as syntax rather than run and interrupted.

A dedicated Web Worker owns the fixed 60 Hz simulation. Canvas2D renders original suspended-foundry artwork from snapshots; React does not own entity physics. This deliberately replaces the planning document's proposed QuickJS/Phaser implementation with a capability language and original renderer. It is not arbitrary game-code generation.

## Source language

Source programs retain literal `version: 1`; the compatible engine is `last-light/2.0.0`. Source has one to eight clauses. A clause queries `player`, `prop`, `lantern` or `ember`, combines `all`/`any`/`not` comparisons, and performs up to six actions. Its optional trigger is `tick` (default), `jump`, `land`, `interact`, `enterZone` or `touch`. Zone entry requires a bounded rectangle. Touch fires on contact entry, and land fires on the tick after landing; remaining in contact or standing on a floor does not repeatedly emit those events. Jump means an allowed jump press. Interact means a rising press near an entity (the courier always receives its own press).

Scalar values can read position, velocity, speed, stillness, grounded state, distance to courier/nearest enabled lantern, tick, timer, held jump/interact input, carried-ember state and extra-jump usage. Validated `add`, `mul`, `min`, `max` arrays and `clamp` objects allow arithmetic composition. Intermediate arithmetic saturates to ±10,000; division and dynamic code are unavailable. Expression evaluation has an independent depth bound.

Actions are generic capabilities:

- `physics` changes gravity scale (0.3–2), jump strength (0.5–1.6), extra air jumps (0–2), courier scale (0.6–1.6), local integration speed (0.5–1.5), or horizontal wind (±0.18). Conditions can restrict effects to zones or entities. Scaling preserves the feet and refuses growth through solid geometry. Local time scale changes entity integration, not simulation ticks, TTLs or the authority heartbeat.
- `material` changes friction (0.65–0.99) and restitution (0–0.95). Physics and material actions support bounded lifetimes, allowing a touch event to make a crate bouncy for exactly 180 ticks (three seconds). When effects expire, ordinary properties return. Later matching modifiers override earlier matching modifiers.
- `projectShadow` projects a silhouette from the nearest enabled lantern to the entity's feet plane and creates a temporary surface. The generated program supplies the relationship between stillness and collision. There is no `shadowBridge` preset, and cosmetic baseline shadows never collide.
- `createSurface` refreshes a bounded surface relative to an entity. `spawnPlatform` creates a distinct temporary surface at a trigger/tick, with a per-clause cap. `spawnProp` creates a temporary 28×40 crate with a cooldown and per-clause cap. Spawned props cannot recursively spawn more props. Every surface action enforces its per-clause cap and the shared 48-surface cap. Capacity and invalid geometry skip further creation and record diagnostics; they do not throw a live runtime fault. The verifier accepts skips at a clause’s own cap. Separate diagnostics reject attempts beyond the shared global budgets, and invalid geometry still rejects. When a clause has already reached its own cap, that skip is not counted as a global denial even if the global budget is exactly full.
- `impulse` adds components clamped to ±2; total velocity is capped at ±20. `cue` applies approved visual emphasis, and `timer` sets a per-entity countdown.

Constant physics and impulse values outside their capability limits reject compilation; arithmetic results saturate to the action's bounds. All numbers must be finite. The complete exact API is exported as `RULE_API_DOCUMENTATION` for the trusted generation coordinator.

### Horizontal surface motion

`createSurface` and `spawnPlatform` accept optional literal `motion: { travel, speed }`. Travel is signed: −240 through −20 moves left of the anchor, and 20 through 240 moves right. Speed is 0.3–2.5 world units per simulation tick. Vertical motion and extra motion fields are rejected. The complete path, including the surface width, must fit inside x = 0–2500. Moving surfaces use the existing clause limits and shared 48-surface budget.

The initial anchor is the owner's x plus `offsetX`, and the top is the owner's feet plus `offsetY`. Both stay fixed while a moving surface is refreshed. Position follows a triangle wave of the absolute simulation tick between the anchor and anchor + travel; a sweep takes `abs(travel) / speed` ticks. Creation at a later tick starts at that clock's phase. Refreshing a one-tick surface preserves its anchor and phase, including when its owner moves. An expired surface that is created again receives a fresh anchor. A spawned platform has its own lifetime and anchor; motion never extends either action's lifetime.

Before each integration step, entities grounded on the previous moving surface receive its horizontal displacement. This includes props and a dropped ember; lanterns remain immovable and the carried ember follows the courier. A prop cannot stand on its own generated surface, matching existing collision behavior. Carry does not add velocity or multiply with an entity's time scale, so normal walking, jumping and departure still apply. Last collision order resolves overlapping supports. The renderer gives every moving generated surface a flat walkable top, tapered brass underside and mint trail in both live play and preview; the collision remains its flat top.

Checkpoints store the initial anchor, initial creation tick and previous x alongside the granted travel and speed. Restore validates the exact analytic current and previous positions, speed, full travel bounds, initial owner-relative placement and matching source action. Lantern anchors are checked exactly; moving owners use a bounded history allowance from initial creation, as other temporary geometry does. The absolute clock and serialized anchor permit exact replay, saved continuation and activation rollback without hidden oscillator state. This capability is additive within `last-light/2.0.0`; programs without motion keep their existing hashes and verifier reports.

The generation contract states the Broken Crossing edges (arrival x = 610, foundry x = 950, both y = 448), the lower stepping stones, the courier's baseline jump and run measurements, and the immovable lantern anchors at x = 320/1030/1840. It contains no named moving mechanic or example law. The [regression evidence](evidence/surface-motion-2026-11-02/README.md) binds the backward-compatibility baseline and synthetic traversal checks.

## One world, three ordered laws

The world contains a courier, three authored movable crates, three lanterns, and exactly one protected physical ember. A/D or arrows move; Space jumps; E moves a nearby crate, toggles lanterns or operates the authored Counterweight Hall/Warden encounters; Q drops or picks up the nearby ember; R recovers at the most recent checkpoint. Dropped ember physics can bounce, while pickup resumes ordinary carried behavior. Generated actions cannot drop, pick up, steal, delete or duplicate the ember. Finishing the objective requires carrying it. Falling recovers the protected objective.

`composeRulePrograms` accepts one to three strict original programs. Two or three produce deterministic namespaced clause IDs and `composition.members` containing the ordered originals. `validateRuntimeRuleProgram` revalidates each original, rebuilds the entire derived program, and compares it with the supplied IR. A composition marker cannot authorize arbitrary extra rules, nested compositions or modified derived actions. Source compilation never accepts composition metadata.

The combined runtime has up to 24 clauses. Laws execute in retained order; later matching property modifiers take precedence. They share the same global command, entity, temporary-surface and modifier limits. Individual verification is insufficient: `verifyRuleComposition` simulates the actual combined program. A combined command flood can therefore fail even when all individual members pass. Approval and artifact hashing are server responsibilities and must bind the ordered candidate identities, engine version, combined program and preview context. An engine-1 save is never silently restored as engine 2; the backend provides explicit upgrade and fresh approval while preserving history.

## Limits and recovery

Each source is limited to 24,000 characters, 1,600 tree nodes, depth 16, eight clauses, six actions per clause and six children per compound condition. Scalar evaluation depth is limited to 12; composition data is bounded to three such sources and their deterministic expansion. A tick queries at most 32 entities and applies at most 128 commands across the entire stack. Excess commands are skipped with a diagnostic. Rising entities are bounded at y = −80 with upward velocity cleared and a recovery diagnostic recorded. Ordinary ceiling contact is accepted; held-input stress rejects more than 30 consecutive ticks with any entity at the ceiling. The world holds at most 12 temporary props (20 total entities), 48 temporary surfaces and 48 timed modifiers. Creation and modifier lifetimes are 1–600 ticks. A spawn clause permits at most four props; a platform clause at most eight surfaces. Shadow projection length is at most 480 world units. All commands operate against copied state before commitment and resource validation.

Strict checkpoints preserve all eight authored identities, their base sizes, the unique ember, immutable baseline route geometry, bounded spawned identities and lifetimes, previous positions/grounded/input state, and timed modifiers. Every non-authored entity must carry a matching spawn grant, within both the per-clause count and global twelve-prop limit. Tick-dependent grant expressions use the saved simulation tick, including ticks beyond 10,000. The checkpoint parser validates the exact runtime program and artifact identity. Saves round-trip through JSON and continue deterministically. No runtime capability exposes the DOM, files, network, process state, provider secrets, progress mutation, teleportation or checkpoint editing.

The worker sends a wall-time heartbeat every 20 seconds even while paused. Only the active host consumes it for lease renewal. Runtime fault messages capture the faulted artifact and tick before local rollback; command errors have a separate protocol and do not retire an active law. The viewport exposes pause, reset, exact checkpoint/restore, activation, rollback and immediate heartbeat requests. Runtime faults pause the authority and restore the prior validated checkpoint. A repeated fault with no previous checkpoint retires every law, cleans temporary entities, surfaces, modifiers, timers and extra-jump use, and preserves the saved authored world and progress. The server clears active identities and advances the revision so the next checkpoint can save normally. After any recovery conflict the client stops automatic retirement requests; “Continue without laws” explicitly saves a law-free checkpoint under fresh revision and existing artifact/authority checks. Manual restore behavior is unchanged.

## What verification establishes

The trusted verifier checks the strict source/derived IR, runs baseline comparisons across idle, movement, extra-jump, interaction and dropped-ember scenarios, and checks continuous held jump/interact/left/right inputs for 600 ticks each. Skips at a clause’s own surface or spawn cap are accepted. Global command, surface, spawn and modifier budget denials and invalid geometry reject; ordinary ceiling recovery is handled separately by the sustained-contact stress check. Physics must change position or size by more than four world units in controlled finite comparisons that stop scoring before route or recovery discontinuities; a 0.999 gravity multiplier cannot pass merely by changing metadata, and a cosmetic cue cannot conceal an ineffective physics modifier. Physics comparisons include a 150-tick dropped-ember scenario that scores the ember’s own trajectory and dedicated 420-tick late-onset scenarios with a jump at tick 320 and an extra jump at 332 in the double-jump case. A third 420-tick late-onset scenario drops the ember at tick 320 without an initial jump, measuring delayed ember-only physics. There are ten controlled scenarios per authored start location; the other seven retain a 150-tick window. Air-jump trials explicitly press jump again while airborne, including while interact is held. Laws without physics actions skip the identical controlled physics comparison but still run actual-effects, held-input safety, replay, rollback and continuation checks. Below-threshold candidates fail with “No noticeable effect on play.” The suite also checks deterministic replay, exact rollback and JSON continuation/cleanup. Reports contain eight check results: bounded capability schema; actual effects and protected invariants; controlled gameplay comparison including airborne jumps; held-input stress and runtime budgets; observable behavior; deterministic replay; exact activation rollback; and JSON checkpoint continuation with temporary cleanup. They also include actual simulated-tick counts and effect counts, including applied modifiers and spawned entities. These finite scenarios do not prove global solvability or natural-language fidelity.

`tests/runtime-engine2.test.ts` contains explicitly synthetic comparative experiments for all ten frozen intent requests and held-out combinations. Additional tests cover exact previously generated source, aggregate flooding, forged composition, bounds, lifetime expiry, deterministic spawning, checkpoint corruption and protected identities. These are engine tests, not claims that fresh Codex generations or browser intent checks have succeeded. The immutable evaluation and real provider/browser results are recorded separately by the release owner.

`PRACTICE_RULE_SOURCE` is deliberately prewritten and must remain labeled as practice. Previously generated artifacts retain their original provenance; a candidate preview runs its exact compiled behavior. All scene art is original procedural Canvas2D work in `src/game/renderer.ts`.

Generation progress contains recorded milestones only: a restored dependency snapshot (only on an actual cache hit), a prepared cold workspace, authoring thread/turn, received source, verifier entry and completed check totals. The completion label uses the actual report numerator and denominator, including failures. Source-derived prose never becomes a progress label. `canonical()` in `src/game/rules.ts` remains unchanged and serves a local equality check when validating derived composition. Artifact hashes use `canonicalJson` in `src/server/security.ts`; the local equality helper is not the hash serializer.
